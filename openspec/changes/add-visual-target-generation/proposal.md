## Why

闭环目前要求用户自己提供目标：`visual_quality_loop.py` 的目标锁定以 `source_path` 为入参，其规格原文是"用户从授权目录提供目标图片或视频证据"。而 dream-loop 方法论中价值最高的一环恰好相反——智能体先自己生成"梦想目标"，再朝它迭代；其技能文档把这一步称为 "The key piece of Dream Loop"。

缺这一步会让闭环退化为"用户随手给一张参考图"：目标质量直接决定迭代上限，而用户往往没有理想目标图。插件本身具备图像生成能力，因此"生成目标"天然在能力范围内，属于把已有能力接上。

同时，dream-loop 的编排工作流中"用全新空上下文的 worker 只负责实现、由编排者负责验证"这一纪律完全没有被固化；现有实现只固化了评审者的 fresh-context 约束。缺少 worker 侧纪律会导致实现者同时充当自己的验收者，评审的独立性被削弱。

## What Changes

- 新增目标获取流程（技能层）：当用户未提供目标时，用图像生成能力产出目标图；当已存在产物时走**基线精修**——以当前状态为输入生成改进版，使目标是原产物的收敛而非方向漂移。
- 固化**反概念艺术纪律**：目标必须是精确、可逐项对照的成品呈现，而不是风格化演绎或艺术诠释。当前仓库中 "concept art" 只作为风格词条出现在提示词词表中，从未作为禁令出现。
- 目标获取失败关闭：无图像生成授权或用户未确认时停止并询问，不静默降级。
- 目标来源记入既有目标回执的 `source` 字段（无需改 Schema）；同时对生成类目标记录是否套用了反演绎纪律。
- 新增 worker 委托纪律：worker 使用全新空上下文（禁止 fork）、只接收高层目标指令而不接收逐条任务与主观意见、只负责实现不负责验证、不得自行启用视觉循环。
- harness 补入目标获取步骤与 worker 委托边界；新技能按仓库供应链规则登记。

## Capabilities

### New Capabilities
- `visual-target-generation`: 目标素材的获取与锁定——生成式目标、存量产物的基线精修、反演绎纪律、生成来源的可追溯记录，以及无授权时的失败关闭。
- `visual-repair-delegation`: 修复轮次的委托纪律——worker 的上下文隔离、指令粒度上限、验证职责归属，以及禁止 worker 自行发起循环的边界。

### Modified Capabilities
（无。目标获取与委托纪律都是新增行为：既有循环的目标锁定接口已接受任意来源映射，Schema 与状态机无需改动。`visual-quality-loop` 能力另有归属，见 `wire-visual-quality-loop` 中关于归档顺序的说明。）

## Impact

- 新增：目标获取技能（含 rubric 同级的参考文档与示例）、worker 委托参考文档、对应测试。
- 修改：`skills/dreamina-design-harness/SKILL.md`（目标获取步骤与委托边界）、`skills/dreamina-vision-judge/SKILL.md`（与目标获取的衔接）、`plugin-local-skills.json`（登记新技能）、`docs/visual-quality-loop.zh_CN.md`。
- 依赖：复用既有图像生成能力与其付费门禁；不引入新依赖、不调用新供应商。
- 兼容性：纯增量。既有循环的目标锁定行为与既有目标回执 Schema 保持不变。
- 费用：目标生成本身是一次付费生成，必须在用户授权与既有门禁下发生；本变更不引入任何自动重试。
- 前置依赖：闭环的 MCP 可达性由 `wire-visual-quality-loop` 提供。在该变更落地前，本变更只能以技能与文档形式存在，不得声称目标获取可在闭环中端到端执行。
- 非目标：不移植 dream-loop 的 Fal 队列助手与本地预览服务器；不做远端发布与真实付费验收。
