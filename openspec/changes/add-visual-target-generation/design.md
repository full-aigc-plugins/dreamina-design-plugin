## Context

本设计要解决的是"目标从哪来"与"修复由谁做、验证由谁做"。当前相关约束：

- 目标锁定接口已接受任意来源映射并写入目标回执，因此新增生成类来源**不需要**改 Schema 或状态机。
- 插件自身具备图像生成能力，且其付费提交已受审批、账本与提交防重约束。目标生成因此是一次普通的付费生成，不构成新的付费通道。
- 仓库存在严格的真值门禁：工作树中的测试会断言未实现的能力不得被声称。目标获取在闭环端到端可达之前，只能以技能与文档形式存在。
- 既有实现已固化**评审者**的 fresh-context 约束（评审技能要求评审上下文的 `fresh_context` 为真且未看过提示词草稿），但未固化 **worker 侧**的任何约束。
- 循环的重试受精确指纹与信用额度上限约束，默认至多一次。目标生成若被错误地当作"重试"，会与这套语义冲突。

## Goals / Non-Goals

**Goals:**

- 让"取得目标"从用户责任变为系统能力，且与用户提供目标享有同一锁定强度。
- 把 dream-loop 中两条尚未迁移的纪律（反演绎、worker 隔离与职责分离）落成可校验的规格。
- 保证目标生成不引入新的付费通道、不引入自动重试、不污染既有回执闭合性。

**Non-Goals:**

- 不修改循环状态机、回执 Schema、额度语义与停滞判定。
- 不把目标生成实现为循环的"重试"动作——它与重试的额度语义不同。
- 不移植 dream-loop 的 Fal 队列助手、图像转三维流水线或本地预览服务器。
- 不在本变更内实现宿主侧评审适配器。
- 不做远端发布与真实付费验收。

## Decisions

### 1. 目标获取位于技能层，而不是领域层

目标获取写成技能与其参考文档（流程、纪律、失败路径与示例），领域层只承接"锁定一个带有来源信息的目标"。

**理由**：目标获取是判断性工作（该生成什么样的目标、何时该走基线精修），依赖模型判断而非可枚举的领域规则；而锁定与校验是确定性的，已在领域层。分层与既有约定一致——方法论在技能、回执与状态机在领域代码。

**备选**：在领域层实现一个"生成目标"的服务方法。否决原因是它会把提示词纪律与风格判断写进领域代码，与该仓库"领域代码不导入客户端 SDK、不承载方法论"的分层相冲突。

### 2. 生成类目标复用既有目标回执的来源字段

生成的来源信息写入既有目标回执的 `source` 映射，区分用户提供与系统生成，并记录生成请求标识与时间。

**理由**：目标锁定接口本就接受任意来源映射，且回执已做闭合校验。这样既获得可审计性，又不需要改 Schema、不需要数据迁移，也不触碰归档中的契约。

**备选**：新增一个专门的"生成目标回执"类型。否决原因是它会造成两类目标回执并存，并让循环需要分支处理两种目标形态，收益不足。

### 3. 基线精修采用"以当前状态为输入"的单步收敛

当已存在产物时，先取得当前状态，再以其为生成输入产出改进版目标。

**理由**：没有这一步，生成的目标会与现有产物在主体、构图或方向上发生漂移，评审的四个维度会同时大幅偏离，迭代难度反而高于没有目标。以当前状态为输入能把目标约束在"同一方向的更好版本"。

**备选**：无条件生成全新目标。否决原因是它会与用户已有的创作方向冲突，且用户已投入的产物无法复用。

### 4. 反演绎纪律写成"生成意图约束"而非"禁用词表"

规格要求目标必须是可逐项对照的成品呈现，并在生成意图描述中避免把结果推向演绎风格的表述；示例中给出正反两例，但不把它固化成一份脆弱的禁用词清单。

**理由**：词表会随模型与语言漂移而失效；纪律要表达的是**意图类别**（可对照的成品 vs 风格化诠释），可校验点是"目标与候选是否同一呈现类别、是否可比对"。

**备选**：维护一份禁用词常量并在代码中断言。否决原因是它把风格判断退化为字符串匹配，且必然过期。

### 5. worker 委托纪律与目标获取同属一个变更

两条纪律都是技能层方法论，且都不改动领域代码；合并可减少一次版本与归档周期。

**理由**：它们共享同一前提（独立的评审与实现），且合并后"评审者隔离 + worker 隔离"形成完整的职责分离图景。若拆开，中间态会出现"评审独立但实现者自证"的半隔离状态，反而不易审查。

**备选**：拆成独立变更。否决原因是两者耦合（角色分离是共同目标），拆分收益仅是归档更细。

### 6. 委托不给逐条任务清单，是刻意的取舍

规格明确要求委托内容不包含逐条修复任务，也不把上一轮的评审清单当作任务单派发。

**理由**：委托方通常弱于被委托方；把弱方的逐条判断当作强方的工作边界，会把最终质量锚定在弱方的水平。让 worker 自行判断如何收敛差距，才能发挥其能力上限。

**权衡已记入本文件的风险段：这会让单轮结果偏离评审点的风险上升，因此必须以"编排者负责验证"作为配套约束，而不是单独采用。

## Risks / Trade-offs

- [委托不给逐条任务，单轮可能偏离评审关注点] → 配套强制"验证职责属于编排者"：编排者在 worker 返回后自行验证，必要时修正装配类问题，再进入下一轮；偏离会在评审环节被再次捕获，而不是被当作完成。
- [目标生成本身是付费动作，可能被用户视为意外花费] → 目标生成与既有付费提交走同一门禁，需要用户明确授权；未授权时失败关闭并请求用户提供目标。
- [把目标生成误当作重试，破坏额度语义] → 目标生成发生在锁定目标之前，早于任何轮次；规格把它定义为目标获取而非轮次，不消耗重试额度，也不产生轮次回执。
- [生成目标与用户目标强度不一致，成为绕过校验的缺口] → 规格要求两者享有同一套摘要、尺寸、媒体类型与授权目录校验，且进入循环后均不得被静默替换。
- [在闭环可达之前声称端到端可用，触碰真值门禁] → 本变更以 `wire-visual-quality-loop` 为前置；在该变更落地前，文档表述限定为技能与方法论，不声称可在闭环中端到端执行。
- [新技能未登记成为供应链孤儿] → 新技能必须登记进 `plugin-local-skills.json`；并注意 `verify_skill_snapshot.py` 与 `validate_distribution.py` 只枚举清单文件、不扫描目录，因此必须以 `skill_vendor check` 的退出码作为真实判据。
- [新技能误用上游命名空间导致未来同步撞名] → 技能名不得使用 `dreamina-prompt-*` 前缀；该前缀属上游技能家族。

## Migration Plan

1. 先写失败测试：无目标时可取得目标、生成目标与用户目标同等校验、未授权时零付费请求、委托内容不含逐条任务。
2. 编写目标获取技能及其参考文档（流程、反演绎纪律、基线精修、来源记录、失败路径）与示例。
3. 编写 worker 委托参考文档与角色分离说明。
4. 更新 harness 的目标获取步骤与委托边界；更新评审技能与目标获取的衔接。
5. 登记新技能进插件本地技能清单，并核对上游命名空间未被占用。
6. 运行目标测试、全量测试、分发校验、`skill_vendor check`、TRACE 与严格 OpenSpec 校验。

**回滚策略**：本变更不改领域代码与 Schema，回滚只需移除新增技能与文档并还原 harness 表述；已写入的生成类目标回执保留来源字段，对旧版本无副作用。

**前置依赖**：闭环的端到端可达性由 `wire-visual-quality-loop` 提供；两者可并行开发，但本变更不得先于前者声称端到端可用。
