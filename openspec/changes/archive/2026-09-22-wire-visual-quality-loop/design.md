## Context

视觉循环的领域实现已存在且测试齐备，但没有任何生产调用方，因此本设计要解决的是**装配与暴露**，而不是领域逻辑。当前相关约束：

- `VideoProjectRuntime` 是十个视频项目工具的组合根，其 `registry()` 断言 handler 集合与 `PROJECT_TOOL_NAMES` 完全相等。该集合语义是"视频项目工具"。
- 生产服务 `DreaminaMcpTools` 在 `call()` 中先做闭合 Schema 校验，再经 `project_tools.handles(name)` 分流；工具表由 `_tool_definitions()` 拼接。
- 既有付费路径已有唯一模板：`_submit_image` / `_submit_video` 走 capability snapshot → reference policy → `ApprovalGuard` → `OperationLedger` → `submit`，并要求用户确认。
- 循环的 `media_kind` 支持 `image` / `video` / `dcc_preview`，首轮路径以图片为主，因此它天然不是"视频项目工具"。
- `integrate-visual-quality-loop` 尚未归档；`visual-quality-loop` 能力尚未同步进 `openspec/specs/`。
- 该仓库存在严格的真值门禁（工作树中的测试会断言未实现能力不得被声称），因此任何文档与 harness 表述必须与已落地事实一致。

## Goals / Non-Goals

**Goals:**

- 以一个独立的装配单元把已实现的闭环接入生产 MCP 工具面，并让它对智能体可发现。
- 保证循环的付费生成只有一条通道，即既有审批与账本通道。
- 让"是否真的可达"成为可自动验证的事实，而不是依赖人工核对。

**Non-Goals:**

- 不改动循环领域状态机、回执契约、额度语义与停滞判定。
- 不为 `visual-quality-loop` 写增量需求（避免与未归档变更产生归档顺序依赖）。
- 不实现宿主侧评审适配器（属宿主层交付物，见变更 `add-visual-target-generation`）。
- 不移植 dream-loop 的 Fal 执行器与本地预览服务器。
- 不做远端发布与真实付费验收。

## Decisions

### 1. 循环使用独立组合根，不并入视频项目运行时

新增独立的装配单元，形状对齐 `VideoProjectRuntime`（持有 `state_root` / `approval_provider` / `adapter_factory`，对外提供注册、归属判断与调用三件事）。

**理由**：循环是跨介质协调器，`media_kind` 含 `image` 与 `dcc_preview`；把它塞进视频运行时会让 `PROJECT_TOOL_NAMES` 的集合断言从"事实"变成"谎话"，也会让"视频项目工具"这一语义失效。

**备选**：把循环工具直接加进 `PROJECT_TOOL_NAMES`。否决原因是它同时污染集合语义与既有断言测试，且后续再接图像侧工具时无处安放。

### 2. 单一工具 + action 枚举，而不是每个动作一个工具

工具面采用一个闭合输入的工具，action 枚举覆盖创建、锁定目标、首轮、重试、重规划提案、状态与停止。

**理由**：与既有项目工具的风格一致（`dreamina_video_project` 即 action 枚举），避免 11 个工具表项各写一份相似 Schema；且循环的有序状态机适合由单一入口串起来，减少客户端把动作调错顺序的机会。

**备选**：每个动作一个工具。否决原因是工具表膨胀、Schema 重复，且无法在 Schema 层表达动作顺序约束。

### 3. 付费通道唯一性由适配器复用既有服务实现

付费生成适配器内部走与 `_submit_image` 完全相同的链路，不自建提交、审批或账本逻辑；适配器只负责把服务返回映射成循环要求的闭合证据结构。

**理由**：设计文档已确立"循环控制器不直接绕过现有服务"（`integrate-visual-quality-loop` Decision 3）。把该约束落在适配器上是唯一能同时满足领域纯净与付费安全的位置。

**备选**：让循环直接调用供应商 CLI。否决原因是它会绕过审批、账本与提交防重，是本次改动最可能造成付费事故的路径。

**实施期澄清（决策 3 的具体形态）**：一次轮次在实现上是"提交 → 轮询 → 下载"三步，因为 `ImageService.submit` 以 `--poll 0` 提交，只返回 `submit_id` 而不落盘（`image_service.py:297-301`），而循环的证据契约要求本地文件加内容摘要。适配器因此复用**两个既有的公开付费工具处理器**（提交与带授权下载目录的任务查询），而不是重新实现它们：提交步骤经由既有提交处理器拿到 `submit_id`，下载步骤经由既有的任务查询处理器在授权目录内轮询并下载，其返回值已包含 `{path, mime_type, size_bytes, sha256}`，补上 `submit_id` 即构成循环要求的闭合五元组。

这样做使付费通道唯一性成为**结构性事实**而非约定：适配器没有自己的提交或下载代码，两个特权步骤各自的审批提示也原样保留。

**备选**：把 `_submit_image` 的链路抽成可复用方法再让适配器调用。否决原因是它需要改动既有付费处理器及其测试，而收益与"直接复用公开处理器"相同；在付费路径上减少改动本身即是收益。

### 4. 产物映射采用"重新校验"而非"信任传入值"

映射层写入回执前重新计算摘要与字节数，并要求证据结构字段完全闭合（提交标识、路径、摘要、字节数、媒体类型五者齐备，不接受额外字段）。

**理由**：已有领域约束如此（`_artifact` 会重新哈希并拒绝被改动的产物）。适配器若预先"填充"字段而不校验，会把领域层的失败关闭变成形式主义。

**备选**：直接透传服务返回值。否决原因是那将依赖上游字段恰好匹配，且丢失"生成后是否被改动"的检测。

### 5. 可发现性纳入本变更，而不是另开文档变更

harness 技能、路由技能与命令层在本变更内一并更新。

**理由**：可达但不可见的闭环等于没有价值——这正是本次问题的成因。且该仓库重视"提交自洽"（相邻变更即在同一提交内修复供应链缺口）。同时修正 harness 声明技能数与实际目录数不一致的陈旧表述，并为其补一条校验，防止再次漂移。

**备选**：拆成独立文档变更。否决原因是拆分后中间态会出现"已接线但无人知晓"，且两者必须同时为真才不违反真值门禁。

**实施期约束（路由技能不可本地修改）**：`dreamina-design-use` 是上游锁定技能——它在 `skills.lock.json` 中被钉到 `dreamina-skills@v1.6.2` 并带逐技能 sha256。本地改动它会让 `skill_vendor check` 以非零状态失败（实测报 content differs from the lockfile digest），并会在下次 vendor 同步时被覆盖。因此本变更的发现路径只落在**插件本地**界面：`dreamina-design-harness`（插件本地清单内）、`commands/`、`docs/`。若将来需要让路由技能也指向闭环，必须**向上游提交**该改动，而不是在插件仓内打补丁。当前库存共 21 个技能 = 17 个上游锁定 + 4 个插件本地，README 中原先"13 pinned"的表述已一并校正为 17。

### 6. 验收以真实分发路径为准

回归测试经服务公开分发入口断言工具存在性、Schema 闭合性与 action 语义；仅直连领域服务的测试不构成验收证据。

**理由**：本次问题的本质就是"库测试全绿而集成缺失"。用同一类测试去验证接通，会重复同一个盲区。

**备选**：复用既有 `tests/test_visual_quality_loop.py`。否决原因是它直接构造服务，恰好绕过了缺的那一层。

### 7. 轮次拆分为"生成"与"记录评审"两个宿主可见步骤（实施期修正）

领域服务的 `_run` 把付费生成与评审融合在一次同步调用中：`reserve_round → generation_port.generate → judge_port.evaluate → record_round`（`visual_quality_loop.py:455-486`）。但评审按本变更决策 3 与本仓分层要求必须由**宿主**提供 fresh-context 视觉子代理，而生产服务是一个 stdio MCP 进程，无法在自己的进程内启动子代理。因此融合调用在 stdio 服务中**结构上不可达**——这正是闭环此前无法接线的根因，而不只是"没有调用方"。

工具面因此把一轮拆成两个宿主可见步骤：

1. `run_first_round` / `run_retry`：预留轮次并执行付费生成，返回产物与证据包，循环停在等待评审的状态；
2. `record_judgement`：接收宿主评审产生的结构化结果，写入轮次回执并返回下一动作。

`propose_retry` 同理改为由调用方提交修复请求，而不是由运行时调用 `ReplanPort`——重规划同样是判断性工作，属宿主职责。运行时只装配领域存储与既有付费服务，不再调用融合的 `_run`，而是组合其底层的存储原语（`reserve_round` / `record_round`），使领域状态机保持唯一权威。

**理由**：这是让"宿主无关评审"与"stdio 进程"两个既有约束同时成立的唯一结构。领域状态机、回执契约与额度语义均不变，只是把原本隐式的进程内回调显式化为两次工具调用。

**备选**：在运行时内实现同步评审适配器。否决原因是它要么把视觉模型 SDK 引入领域层（违反分层），要么伪造评审结果（违反独立评审的成立条件）。

**备选**：把 `JudgePort` 实现为抛"评审待定"的哨兵并在失败路径吞掉异常。否决原因是它会把"评审未发生"伪装成"轮次已执行"，破坏诚实语义。

**影响**：规格中"首轮执行"与"重试执行"的语义由此明确为**付费生成步骤**，评审结果另经 `record_judgement` 记录；规格的其余要求（付费通道唯一、首轮失败不自动二次付费、额度绑定指纹）不受影响。

## Risks / Trade-offs

- [适配器绕过付费门禁，造成未经授权的付费提交] → 适配器只允许复用既有服务链路；新增测试断言未授权时零付费请求，并断言审批与账本条目格式与直接生成路径一致。
- [新增工具与 `PROJECT_TOOL_NAMES` 集合断言冲突] → 使用独立组合根与独立工具表项；若沿用视频运行时则必须同步修改集合与断言，本设计从结构上避免该冲突。
- [harness 声明与技能目录再次漂移] → 新增技能数量一致性校验，使漂移变为测试失败而非静默通过。
- [文档声称尚未具备的能力，触碰真值门禁] → 本变更只在能力落地后更新文档，且表述限定为已实现事实；不声称自动目标生成、不声称自动重试、不声称远端取消。
- [并行会话在同一仓库编辑，误提交他人改动] → 动手前检查工作树状态；提交前区分自己写入的文件；撤销使用 `git reset --mixed` 而非 `--hard`。
- [工具表数量变化使既有计数断言失效] → 同步更新工具表、README 与分发校验断言，并把数量变化纳入本次提交。

## Migration Plan

1. 先写经真实分发入口的失败测试（工具缺失、Schema 不闭合、action 非法），确认其在当前实现下失败。
2. 实现独立组合根与工具 Schema，注册进服务工具表与分发分支。
3. 实现付费生成适配器与产物映射，接入既有审批、账本与提交防重。
4. 更新 harness、路由技能与命令层，使闭环可被发现，并修正技能数量表述。
5. 一致性收尾：工具表、README、分发校验断言、`dreamina-vision-judge` 的登记状态核对。
6. 运行目标测试、全量测试、分发校验、TRACE 与严格 OpenSpec 校验。

**回滚策略**：移除工具表项与分发分支即可回到"领域已实现但不可达"的当前状态；循环状态目录对旧版本不可见，已写入的回执与状态文件不需要迁移。

**归档前置**：`integrate-visual-quality-loop` 的 16 项任务已全部勾选，应在本次改动落地后一并归档，使 `visual-quality-loop` 同步进 `openspec/specs/`。
